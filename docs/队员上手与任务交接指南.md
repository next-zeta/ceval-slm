### 5.1 使用官方站下载

以上环境变量只在当前窗口有效；新开窗口后需要重新设置离线变量并激活虚拟环境。

### 5.2 Windows 出现 WinError 1314

这是创建符号链接权限不足，不代表权重损坏。打开 Windows 设置中的“开发人员模式/开发者模式”，确认开启后重试同一下载命令，复用缓存即可。不要用关闭证书校验解决权限问题。

组员也可以由 A 分享已下载的缓存；应保留对应模型目录下 blobs、snapshots、refs 的目录关系与内容，并确认 snapshot 中的链接目标有效。只复制一个带失效链接的 snapshots 目录可能无法使用。

### 7.3 C：3 次采样投票与错误分析

现有投票配置为 n_samples=3、temperature=0.7、top_p=0.9。先审查 vote()：全无效、部分无效、三票各不同和有多数票时如何处理，写清实际规则并覆盖边界测试。当前逻辑会排除无效票再统计，平票优先第一票；若第一票不在并列有效候选中，则取并列候选的首次出现项。不能在看分后换平票规则。

```powershell
python src/run_eval.py --config configs/vote.json --limit 5 --exp_id try_voting_C
python src/run_eval.py --config configs/vote.json --exp_id exp03_voting_C --note "成员C；同本地基线设备与精度；3次采样投票"
```

这是“采样 + 多次生成 + 投票”的整体策略，与 greedy 比较时同时引入额外计算，不能声称单独证明投票模块有效。若要分离投票效应，可预先设计额外的单次采样对照，并明确记录。

200 题对应 600 次单题生成。交付：准确率、格式有效率、生成次数、耗时、输出 token、平票与无效票分析；至少 5 个不同题目的错误案例，覆盖知识、推理、格式、截断等现象，出现改对变错时纳入分析，不能为凑类别编造案例。

### 7.4 D：批处理效率、汇总与消融

先核对当前实现：基线和批处理都已经使用 torch.inference_mode()。因此本轮主要变量应写成 batch_size=1 → 4/8，不能把已经存在的 inference_mode 算成新增加速贡献。保持 prompt 和 greedy 参数一致。

```powershell
python src/run_eval.py --config configs/batch.json --batch_size 4 --limit 5 --exp_id try_batch_D
python src/run_eval.py --config configs/batch.json --batch_size 4 --exp_id exp04_batch4_D --note "成员D；同本地基线设备与精度；仅batch_size=4"
python src/run_eval.py --config configs/batch.json --batch_size 8 --exp_id exp04_batch8_D --note "成员D；同本地基线设备与精度；仅batch_size=8"
```

至少完成一个批大小的正式对照；资源允许再补另一个。加速比 = 本人 batch=1 生成总耗时 / 本人批处理生成总耗时。逐题比较选项一致性，若结果不同需保留并解释，不能仅比较总准确率。

报告中区分“单题生成数”与“generate API 调用数”：当前日志 n_calls 在批处理下仍按每题记 1，200 题显示 200，但 batch=4 时 generate 调用通常为 50 次、batch=8 为 25 次。不要把 200 写成实际批调用次数。

现有 GPU 计时未显式同步，若测 GPU，D 应先完善并验证计时，再在同一实现下重跑自己的基线和批处理。CPU 路线可以沿用当前计时。

四人改进完成后，由 D 根据证据选择最终组合，并做至少一组只移除一个模块的消融。configs/final.json 与 ablation.json 当前只是占位，不能直接把它们当作已经确定的最终方案；组合提示约束和示例可能还需要代码支持。

2. **计时与环境**：同一电脑、设备、精度、线程设置与软件版本完成自己的基线和改进。不同电脑不比较绝对耗时；不同设备/采样实现也不保证输出完全一致，差异应记录和分析。
3. **评分不变**：不要因本次低分接受更多答案格式、替换题目或增加 token。确有评分实现错误时，全组记录原因并统一重评相关实验，保留原日志。
4. **异常记录**：当前运行遇到系统故障可能中止，不能假定已有完善的超时/异常逐题字段。B/C 需审查完善，系统故障保留中断日志，修复后以新实验编号完整重跑，不能只补错题。
5. **原始输出**：当前解码会去特殊 token 并 strip；如果报告声称保存“未清洗原始输出”，B/C 应补充完整生成 token/原始文本及各次采样记录，并明确区分用于解析的文本。已有日志如实说明处理口径。

组员可以先配环境、试跑和采集本地基线；涉及公共实现修正时，由负责人统一提交，再判断哪些对照需重跑。不要四个人各自复制一套评分脚本。

## 9. 结果怎么记、怎么交

### 9.2 提交代码，再跑实验，再提交结果

以下以 B 为例，其他成员换成自己的文件和目录：

## 11. 常见问题速查

| 现象 | 怎么处理 |
| :--- | :--- |
| git 找不到 | 确认安装并新开终端；默认安装位置可按 §3 临时加 PATH |
| GitHub push 拒绝 | 克隆权限与写权限不同；确认已接受协作者邀请，并登录自己的账号；不要强推 |
| PowerShell 不让激活 venv | 直接用 .venv\Scripts\python.exe 执行，无需全局放开策略 |
| 中文 UnicodeDecodeError | 最新 main 已给流水线子进程设置 UTF-8；先更新代码，需要时当前窗口设 `$env:PYTHONIOENCODING="utf-8"` |
| HF 官方或镜像超时 | 先换可达端点再重试；不要删除已下载的缓存 |
| WinError 1314 | 开启 Windows 开发者模式后重试下载，复用缓存 |
| 本地找不到模型 | 确认相同用户/缓存位置、模型下载完成，下载阶段 HF_HUB_OFFLINE=0，运行阶段再设为 1 |
| generation flags 警告 | greedy 时温度等采样参数被忽略；检查 do_sample=False，通常不影响基线运行 |
| 试跑 0 分、格式有效率低 | 查看原始输出，按固定规则记录；不临时放宽解析器 |
| 截断率高 | 记录并分析，截断仍按规则评分；不自行改 16 token；系统性参数分析另建实验 |
| 已有同名日志 | 换新 exp_id 并记录原因，正式结果不覆盖 |
| 准确率分母显示 1 或 3 | 使用了旧版汇总代码，更新到最新 main；正式汇总 n_samples 应为 200 |
| 改进没提升/批处理没加速 | 完整报告负结果，解释预算、格式与输出差异，不编造或挑选结果 |
